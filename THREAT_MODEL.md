# django-auditlog-v3 threat model

## Overview

A Django audit extension registers lifecycle, optional M2M and access signals; computes filtered changes; stores JSON audit entries and optional serialized model snapshots; and supplies contextual actor/correlation attribution and a restricted Django admin. Default persistence uses the LogEntry manager and host routing, not explicit routing to instance._state.db (auditlog/registry.py:61; auditlog/models.py:36; auditlog/models.py:77).

This snapshot packages a version 3 beta of django-auditlog. Registration, serialization, capture suppression and custom callbacks are trusted application choices. The extension can record explicit access events as well as changes, but neither kind of event proves that the caller authorized the operation. Middleware identity depends on the host authentication stack; database and log-reader policy depend on the host deployment.

## Threat Model, Trust Boundaries, and Assumptions

**Protected assets.** JSON changes, optional serialized_data, object representation, additional_data, actor, remote_addr and correlation ID (auditlog/models.py:347; auditlog/models.py:362). Integrity and retention of audit history and release packages (auditlog/admin.py:38; .github/workflows/release.yml:42).

**Actors and starting authority.** A caller-facing user may influence captured data and headers without authority over settings, signal callbacks or database administration. A maintainer able to publish trusted source/tags occupies the package-supply boundary; CI secrets are not user-request inputs.

**Trust boundaries and owned controls.**

- Authenticated request.user is consumed, not authenticated by middleware. First X-Forwarded-For value determines remote address; correlation ID comes from configured request header or trusted callable/import path. ContextVar and signal dispatch IDs scope actor attribution, but nested set_actor calls overwrite the context without resetting its token. With distinct dispatch IDs, inner exit disconnects the inner receiver; later outer logs no longer match the outer receiver, and outer exit tries to disconnect the inner receiver again, retaining the outer receiver (auditlog/middleware.py:17; auditlog/context.py:19-42; auditlog/context.py:45-65; auditlog/cid.py:23; auditlog/cid.py:64).
- Non-M2M create/update/delete/access events pass through _create_log_entry, where pre_log callbacks can veto. Configured M2M handlers bypass that callback path and call LogEntry.objects.log_m2m_changes directly; a pre_log False does not suppress their entries. check_disable gates create/update/delete and configured M2M handlers, while the access receiver lacks that decorator. Access signaling records access but does not grant access to an object (auditlog/receivers.py:11; auditlog/receivers.py:86; auditlog/receivers.py:106). Updates log from pre_save before the model UPDATE; under autocommit a later failed UPDATE can leave its audit insert durable. LogEntry manager routing may select another database, which a model-database transaction does not make atomic. Use a shared database transaction where possible or explicitly distinguish attempted changes from committed changes (auditlog/registry.py:61-66; auditlog/receivers.py:49-66; auditlog/models.py:77). Under Django ORM save-signal semantics, QuerySet.update(), bulk_update() and bulk_create() bypass this capture path; hosts requiring complete history must avoid those APIs or supply equivalent audit records (auditlog/registry.py:61-68).
- serialize_data defaults false; enabling it invokes Django JSON serialization, optionally restricts to tracked fields, and masks only configured string fields. Diff masking replaces the first half of strings; additional_data/object_repr have separate consumers and require caller minimization (auditlog/registry.py:74; auditlog/models.py:224; auditlog/models.py:285; auditlog/diff.py:95). With the default [Django serializer](https://docs.djangoproject.com/en/4.2/topics/serialization/#subset-of-fields), the primary key is outside fields as top-level pk, so tracked-field selection, exclude_fields and _mask_serialized_fields do not remove or mask it. For sensitive primary keys, omit snapshots or verify a serializer/post-processing policy that removes this channel; natural-primary-key serialization can omit pk for suitably implemented models. Independently account for object_pk, which records the identifier regardless of snapshot policy (auditlog/models.py:52-71; auditlog/models.py:224-246; auditlog/models.py:285-298). M2M capture separately stores smart_str() for changed related objects directly in changes and does not consult mask_fields, include_fields or exclude_fields; minimize related-object representations or omit sensitive M2M capture. A pre_log veto does not apply to M2M; enforce an equivalent M2M-specific policy, omit that relation's capture, or use narrowly scoped disable_auditlog around the operation, noting it suppresses other decorated captures in that context too. A task created with the current context inside this scope can retain auditlog_disabled=True after the parent exits: resetting the parent token does not modify the child copy. Do not create detached tasks in a suppression scope unless their audit state is explicitly established and restored before required mutations. This flag governs decorated lifecycle/M2M handlers, not the undecorated access receiver (auditlog/models.py:80-129; auditlog/receivers.py:11-29, auditlog/receivers.py:86-103, auditlog/receivers.py:149-182; auditlog/context.py:12, auditlog/context.py:68-77).
- Admin forbids direct add/change/delete, with a cascade path delegated to Django delete permissions. AuditlogHistoryField(delete_related=True) lets deletion of a tracked object collect its LogEntry rows; the default False preserves them. Host object-deletion authority can therefore affect retention independently of direct LogEntry deletion, while ORM and command access retain their own write authority (auditlog/models.py:550-577; auditlog/admin.py:48-55). Host authentication, model visibility and history-reader authorization remain required (auditlog/admin.py:38).
- Tag release CI is gated to jazzband/django-auditlog, uses read-all permissions and sends built distributions to Jazzband using JAZZBAND_RELEASE_KEY. This copied workflow does not establish active release authority on another fork (.github/workflows/release.yml:3; .github/workflows/release.yml:8; .github/workflows/release.yml:48). Before building, the job upgrades pip, setuptools, twine and wheel without version/hash constraints; the configured package index and these packages are executable release inputs independently of pinned action revisions. Pin and verify build packages and resulting artifacts (.github/workflows/release.yml:37-46).
- Operator JSON conversion has separate consumers: the ORM path selects nonempty changes_text with changes NULL, parses JSON and bulk-updates in batches; --database selects an engine rather than a DB alias. If pending logs exist, native postgres uses django.db.connection to update the full auditlog_logentry table without the ORM selection predicate. mysql/oracle choices raise not implemented. Migration 0015 chooses direct field alteration or a two-step text/JSON split by AUDITLOG_TWO_STEP_MIGRATION (auditlog/management/commands/auditlogmigratejson.py:81; auditlog/management/commands/auditlogmigratejson.py:122; auditlog/migrations/0015_alter_logentry_changes.py:8).

- Update old-state lookup is a separate database consumer: log_update ignores the pre_save using alias and queries sender.objects.filter(pk=instance.pk).first() on normal manager/read routing. With using= or split read/write routing this can read a same-PK row from another database or None and record an incorrect diff. Even on the correct alias, a filtered objects manager can hide an existing row and return None. The diff then compares eligible current values against missing/null old representations instead of database history; field filtering and equality still apply, so not every value is necessarily reported. Use an appropriate unfiltered old-state manager bound to the signal's save database alias and verify any replica/read consistency contract. That internal history read does not replace caller authorization, and correct LogEntry routing alone does not correct old-state selection (auditlog/registry.py:64; auditlog/receivers.py:50-65; auditlog/diff.py:54-92, auditlog/diff.py:143-193). Correct routing and an unfiltered manager do not serialize concurrent writers: the pre_save old-state read is unlocked. Where database isolation allows two saves to read A before either update, they can record A→B and A→C even when the committed transitions are A→C→B. Exact transition history additionally requires row locking before the snapshot through the write, enforced optimistic conflict detection, or equivalent serialization with conflict/retry handling, coupled to the audit transaction (auditlog/receivers.py:50-65; auditlog/registry.py:64).

- Deleting the actor's AUTH_USER_MODEL row clears LogEntry.actor through SET_NULL while retaining the log row, independently of delete_related and direct LogEntry-delete restrictions. Identity-administration authority therefore affects attribution. If attribution must survive permitted account removal, retain an approved stable identity snapshot or tombstone account, or explicitly treat null actor as lost/unknown attribution; align the chosen retention with the host's identity/privacy policy (auditlog/models.py:354-360).

- Pre-save audit values also need not equal the resulting database state after a successful update: F expressions are read/stringified before database evaluation, and the existing test expects an expression string in serialized_data. Treat these entries as submitted expressions/intent, or use verified post-write refresh and explicit audit recording coupled to the correct transaction/database when exact persisted values are required; alternatively avoid database-evaluated assignments on that exact-state capture path (auditlog/receivers.py:49-66; auditlog/diff.py:54-92; auditlog_tests/tests.py:2321-2337).

- Update capture also precedes auto_now field assignment. When normal saving changes a tracked auto_now timestamp after the model pre_save signal, that new timestamp can be absent from the diff; if it is the only effective change, no update entry may be created. Where these timestamps must be audited exactly, use equivalent post-write refreshed logging coupled to the correct database/transaction; explicit update_fields that excludes the timestamp does not update it (auditlog/registry.py:64, auditlog/receivers.py:50-66, auditlog/receivers.py:119-128; auditlog_tests/models.py:22, auditlog_tests/tests.py:159-165).

- The ORM conversion can leave valid rows unmigrated when invalid JSON repeatedly occupies leading batch slots. It fixes the iteration count from the initial pending count but reselects the leading pending slice, retaining failed rows. With 1,000 pending rows, batches of 500 and one recurring leading invalid row, only 998 valid rows migrate and one valid row remains. Quarantine/skip known failures with stable traversal or continue only while measurable progress is made; verify pending counts and failed IDs explicitly rather than equating command completion with migration completion (auditlog/management/commands/auditlogmigratejson.py:81-119). JSON syntax success is also insufficient: json.loads accepts scalars, lists and incompatible mapping values without checking the audit change schema. Truthy non-mappings later fail .items(), and malformed field values can fail or mislead formatters; falsey values can instead become empty changes. Validate/quarantine incompatible legacy shapes before migration and check consumer compatibility after conversion, preserving the distinct ordinary old/new and structured M2M change forms rather than requiring every field value to be a pair (auditlog/management/commands/auditlogmigratejson.py:86-100; auditlog/models.py:119-127; auditlog/models.py:409-474; auditlog/models.py:584-599).

- History lookup has no object-incarnation or source-database key: reusing a primary key under the same content type makes get_for_object include retained entries for the prior object. This can mix timelines and disclose prior-object values even when access to the new object is correctly authorized. If separate source databases send the same model/PK to one audit store with compatible content-type/actor identities, the helper also mixes those simultaneously existing objects; instance._state.db is neither recorded nor used as a selection predicate. Use identifiers unique across the combined history domain, segregated audit stores, or an explicitly recorded and enforced source/generation discriminator where these identities must remain distinct (auditlog/models.py:36-77, auditlog/models.py:133-152, auditlog/models.py:335-379).

- LogEntry routing must also satisfy its ContentType and AUTH_USER_MODEL foreign keys. Splitting audit writes from those identity tables cannot rely on unsupported cross-database foreign-key relations: routing/assignment or insertion can fail, and unmatched copied IDs can misattribute entries. Keep these dependencies compatibly routed with matching identities, or rule out that split; independent audit routing alone establishes neither referential identity nor transaction coupling (auditlog/models.py:36-77, auditlog/models.py:335-361; auditlog/context.py:63).

- Configured reverse-side M2M clearing can fail before the clear: the pre_clear handler resolves the registered forward field_name on the related-side instance and does not handle reverse. When that attribute is absent it raises AttributeError. Reverse-side add/remove also passes the related-side instance to the log manager while retaining the forward field name, so entries can attach to that related object and omit the event from the intended owner history; an independently configured receiver may add other entries. Require forward-side operations for every configured M2M action or a verified reverse-aware handler. Direction alone is insufficient: post_add/post_remove rebuild changed objects through model.objects without the signal using alias, so filtered managers can omit entries and routing can serialize unrelated same-PK objects from another database. Bind an appropriate unfiltered related-object lookup to the mutation database or log explicitly. Also, [Django post_remove pk_set](https://docs.djangoproject.com/en/4.2/ref/signals/#m2m-changed) represents requested removals, not only relationships that existed: resolving an existing but unrelated object can produce a false delete entry. For exact history, capture/intersect through-row membership before removal with appropriate transaction/concurrency handling; otherwise describe these entries as removal requests (auditlog/receivers.py:163-182; auditlog/models.py:98-129). Matching accessor names only avoid the particular clear exception; they do not establish correct ownership for add/remove (auditlog/receivers.py:149-182; auditlog/models.py:98-129). Forward pre_clear also synchronously loads every related object and materializes all smart_str values into one JSON entry before clearing. A caller allowed to clear a high-cardinality relation can therefore impose memory, representation and write-size costs that cause request timeout or failure; no bound is established here. Bound supported relation sizes or design bounded/batched capture (or explicit summary/asynchronous delivery) that preserves the required pre-clear evidence and transaction/recovery contract. Separately, the objects array stores representations without related primary keys: equal smart_str values make distinct related objects indistinguishable. Where durable relationship identity is required, capture a stable related identifier alongside its display value, with database/model identity as needed (auditlog/receivers.py:157-180; auditlog/models.py:98-129).

- Deleting a tracked model ContentType through Django ORM also cascades to its LogEntry rows, independently of AuditlogHistoryField(delete_related=False) and direct admin LogEntry deletion restrictions. Treat content-type cleanup/model retirement authority as retention authority: preserve required content types or protect/archive associated history under an explicit retention policy before removal (auditlog/models.py:335-340, auditlog/models.py:550-577).

- changes_display_dict requires available installed model metadata and current auditlog registration before its field/reference fallbacks run. Unregistering the model can raise KeyError; model_class() returning None can raise AttributeError. For long-lived history after model retirement, retain compatible metadata/registration or provide an authorized stored-value formatter that does not require live model resolution; retained rows alone do not guarantee this helper remains usable (auditlog/models.py:442-452; auditlog/registry.py:178-184). Even with live metadata, choice values are rendered using current field.choices: changed labels reinterpret historical codes, and unrecognized codes display as the literal None string. Stored changes remain intact. Preserve raw codes in authorized output and use a versioned historical mapping when historical labels matter; do not treat present-day display labels as immutable evidence (auditlog/models.py:454-474).

- Direct intermediary-model writes are outside the configured M2M signal path: ordinary ThroughModel create/save/delete operations do not emit the relation manager m2m_changed signal. Registering only the owner with m2m_fields therefore does not capture those mutations. Use supported forward related-manager operations or separately register/log the through model; where consumers require owner-shaped relationship history, map that row capture explicitly rather than assuming it has the same shape (auditlog/registry.py:210-220; auditlog_tests/models.py:338).

- CID lifetime is a separate context boundary. With the default getter, set_cid stores the header value without retaining a reset token, and middleware does not restore it after get_response or on error. Subsequent work in the same context can inherit a completed request CID; a task created during the request can retain its copied value too. Restore the prior CID token in a middleware finally path and explicitly clear or propagate CID for detached tasks according to their ownership. Resetting a parent context does not clear an already-copied child context. Later requests call set_cid again, including None when absent, so this is not a claim of unconditional leakage into every next request or unrelated thread (auditlog/cid.py:12-43; auditlog/middleware.py:43-52; auditlog/models.py:76).

- LogAccessMixin repeats get_object during render_to_response instead of using the object already selected for the response context. Stable PK selection usually preserves identity but still adds a lookup; stateful/changing selection can log a different object, and deletion or another lookup error can prevent the response. Bind the logged instance to self.object or another explicit value used in the rendered context, preserving the host authorization decision (auditlog/mixins.py:165-169). The accessed signal is sent before the superclass render_to_response call. An ACCESS row can therefore precede a failed response construction or later deferred rendering/delivery failure; it establishes an attempted render path, not successful content delivery. Name that event accordingly or separately record the specific successful server-side completion event required by the host; server completion alone does not prove client receipt (auditlog/mixins.py:165-169; auditlog/receivers.py:86-103).

- Lifecycle registration matches the exact model sender. Registering a base class does not automatically capture ordinary saves through unregistered proxy or multi-table subclasses; each actual save sender whose operations require history needs registration or equivalent explicit logging. Verify field coverage and history identity for those classes instead of assuming registration inheritance. This does not imply that all subclass deletion paths lack parent events (auditlog/registry.py:200-220; auditlog_tests/models.py:335-336).

**Security objectives.** Authorize historical data access independently from current-object access. Minimize each persisted channel and distinguish partial masking from complete removal. Keep actor context and correlation metadata distinct from access authorization; preserve intended capture and retention policies.

**Assumptions and unresolved controls.**

- Host routers determine effective database; concrete DB endpoint/credentials and app tenant model are absent.
- JSON migration and auditlogflush are operator workflows, not web APIs; auditlogflush permits --yes and optional before-date selection (auditlog/management/commands/auditlogflush.py:11).
- Host database routing, full read authorization, callback ownership, storage immutability and live publisher settings are unknown. JSON migration/flush behavior is an operator surface; no public command endpoint is established.

## Severity Calibration (Critical, High, Medium, Low)

| Level | Repository-specific example | Counterexample or limiting prerequisite |
| --- | --- | --- |
| Critical | An established release compromise distributes executable code broadly, or a history endpoint exposes a demonstrably critical dataset. | Needs a lower-trust path across actual publication/data-access controls; maintainer intent is not an exploit. |
| High | An unauthorized user obtains another user’s confidential snapshot or sensitive historical values. | A partially masked value is not automatically high severity; its content and usefulness must be shown. |
| Medium | Attribution or retention failure materially breaks a supported security workflow. | Caller-chosen capture suppression and operator purge can be authorized behavior. |
| Low | Limited metadata leakage or local administrative inconvenience. | A correlation ID under user control is not an authenticated credential and is not itself a security defect. |

This model uses an independent source-backed architecture pass. Repository citations were checked against the supplied inventory and source lines; application code and external services were not executed. Source-established behavior is distinct from unverified deployment exposure. Revisit the model when the described input, storage, authorization or publication boundaries change.
