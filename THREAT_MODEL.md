# django-auditlog-v3 threat model

## Overview

A Django audit extension registers lifecycle, optional M2M and access signals; computes filtered changes; stores JSON audit entries and optional serialized model snapshots; and supplies contextual actor/correlation attribution and a restricted Django admin. Default persistence uses the LogEntry manager and host routing, not explicit routing to instance._state.db (auditlog/registry.py:61; auditlog/models.py:36; auditlog/models.py:77).

This snapshot packages a version 3 beta of django-auditlog. Registration, serialization, capture suppression and custom callbacks are trusted application choices. The extension can record explicit access events as well as changes, but neither kind of event proves that the caller authorized the operation. Middleware identity depends on the host authentication stack; database and log-reader policy depend on the host deployment.

## Threat Model, Trust Boundaries, and Assumptions

**Protected assets.** JSON changes, optional serialized_data, object representation, additional_data, actor, remote_addr and correlation ID (auditlog/models.py:347; auditlog/models.py:362). Integrity and retention of audit history and release packages (auditlog/admin.py:38; .github/workflows/release.yml:42).

**Actors and starting authority.** A caller-facing user may influence captured data and headers without authority over settings, signal callbacks or database administration. A maintainer able to publish trusted source/tags occupies the package-supply boundary; CI secrets are not user-request inputs.

**Trust boundaries and owned controls.**

- Authenticated request.user is consumed, not authenticated by middleware. First X-Forwarded-For value determines remote address; correlation ID comes from configured request header or trusted callable/import path. ContextVar and signal dispatch IDs scope actor attribution, but nested set_actor calls overwrite the context without resetting its token. With distinct dispatch IDs, inner exit disconnects the inner receiver; later outer logs no longer match the outer receiver, and outer exit tries to disconnect the inner receiver again, retaining the outer receiver (auditlog/middleware.py:17; auditlog/context.py:19-42; auditlog/context.py:45-65; auditlog/cid.py:23; auditlog/cid.py:64).
- Non-M2M create/update/delete/access events pass through _create_log_entry, where pre_log callbacks can veto. Configured M2M handlers bypass that callback path and call LogEntry.objects.log_m2m_changes directly; a pre_log False does not suppress their entries. check_disable gates create/update/delete and configured M2M handlers, while the access receiver lacks that decorator. Access signaling records access but does not grant access to an object (auditlog/receivers.py:11; auditlog/receivers.py:86; auditlog/receivers.py:106). Updates log from pre_save before the model UPDATE; under autocommit a later failed UPDATE can leave its audit insert durable. LogEntry manager routing may select another database, which a model-database transaction does not make atomic. Use a shared database transaction where possible or explicitly distinguish attempted changes from committed changes (auditlog/registry.py:61-66; auditlog/receivers.py:49-66; auditlog/models.py:77). Under Django ORM save-signal semantics, QuerySet.update(), bulk_update() and bulk_create() bypass this capture path; hosts requiring complete history must avoid those APIs or supply equivalent audit records (auditlog/registry.py:61-68).
- serialize_data defaults false; enabling it invokes Django JSON serialization, optionally restricts to tracked fields, and masks only configured string fields. Diff masking replaces the first half of strings; additional_data/object_repr have separate consumers and require caller minimization (auditlog/registry.py:74; auditlog/models.py:224; auditlog/models.py:285; auditlog/diff.py:95). M2M capture separately stores smart_str() for changed related objects directly in changes and does not consult mask_fields, include_fields or exclude_fields; minimize related-object representations or omit sensitive M2M capture. A pre_log veto does not apply to M2M; enforce an equivalent M2M-specific policy, omit that relation's capture, or use narrowly scoped disable_auditlog around the operation, noting it suppresses other decorated captures in that context too (auditlog/models.py:80-129; auditlog/receivers.py:149-182; auditlog/context.py:68-77).
- Admin forbids direct add/change/delete, with a cascade path delegated to Django delete permissions. AuditlogHistoryField(delete_related=True) lets deletion of a tracked object collect its LogEntry rows; the default False preserves them. Host object-deletion authority can therefore affect retention independently of direct LogEntry deletion, while ORM and command access retain their own write authority (auditlog/models.py:550-577; auditlog/admin.py:48-55). Host authentication, model visibility and history-reader authorization remain required (auditlog/admin.py:38).
- Tag release CI is gated to jazzband/django-auditlog, uses read-all permissions and sends built distributions to Jazzband using JAZZBAND_RELEASE_KEY. This copied workflow does not establish active release authority on another fork (.github/workflows/release.yml:3; .github/workflows/release.yml:8; .github/workflows/release.yml:48). Before building, the job upgrades pip, setuptools, twine and wheel without version/hash constraints; the configured package index and these packages are executable release inputs independently of pinned action revisions. Pin and verify build packages and resulting artifacts (.github/workflows/release.yml:37-46).
- Operator JSON conversion has separate consumers: the ORM path selects nonempty changes_text with changes NULL, parses JSON and bulk-updates in batches; --database selects an engine rather than a DB alias. If pending logs exist, native postgres uses django.db.connection to update the full auditlog_logentry table without the ORM selection predicate. mysql/oracle choices raise not implemented. Migration 0015 chooses direct field alteration or a two-step text/JSON split by AUDITLOG_TWO_STEP_MIGRATION (auditlog/management/commands/auditlogmigratejson.py:81; auditlog/management/commands/auditlogmigratejson.py:122; auditlog/migrations/0015_alter_logentry_changes.py:8).

- Update old-state lookup is a separate database consumer: log_update ignores the pre_save using alias and queries sender.objects.filter(pk=instance.pk).first() on normal manager/read routing. With using= or split read/write routing this can read a same-PK row from another database or None and record an incorrect diff. Bind the lookup to the signal's save database alias and verify any replica/read consistency contract; correct LogEntry routing alone does not correct old-state selection (auditlog/registry.py:64; auditlog/receivers.py:50-65).

- Deleting the actor's AUTH_USER_MODEL row clears LogEntry.actor through SET_NULL while retaining the log row, independently of delete_related and direct LogEntry-delete restrictions. Identity-administration authority therefore affects attribution. If attribution must survive permitted account removal, retain an approved stable identity snapshot or tombstone account, or explicitly treat null actor as lost/unknown attribution; align the chosen retention with the host's identity/privacy policy (auditlog/models.py:354-360).

- Pre-save audit values also need not equal the resulting database state after a successful update: F expressions are read/stringified before database evaluation, and the existing test expects an expression string in serialized_data. Treat these entries as submitted expressions/intent, or use verified post-write refresh and explicit audit recording coupled to the correct transaction/database when exact persisted values are required; alternatively avoid database-evaluated assignments on that exact-state capture path (auditlog/receivers.py:49-66; auditlog/diff.py:54-92; auditlog_tests/tests.py:2321-2337).

**Security objectives.** Authorize historical data access independently from current-object access. Minimize each persisted channel and distinguish partial masking from complete removal. Keep actor context and correlation metadata distinct from access authorization; preserve intended capture and retention policies.

**Assumptions and unresolved controls.**

- Host routers determine effective database; concrete DB endpoint/credentials and app tenant model are absent.
- JSON migration and auditlogflush are operator workflows, not web APIs; auditlogflush permits --yes and optional before-date selection (auditlog/management/commands/auditlogflush.py:11).
- Host database routing, full read authorization, callback ownership, storage immutability and live publisher settings are unknown. JSON migration/flush behavior is an operator surface; no public command endpoint is established.

## Severity Calibration (Critical, High, Medium, Low)

| Level | Repository-specific example | Counterexample or limiting prerequisite |
| --- | --- | --- |
| Critical | An established release compromise distributes executable code broadly, or a history endpoint exposes a demonstrably critical dataset. | Needs a lower-trust path across actual publication/data-access controls; maintainer intent is not an exploit. |
| High | An unauthorized user obtains another user’s confidential snapshot or sensitive historical values. | A partially masked value is not automatically high severity; its content and usefulness must be shown. |
| Medium | Attribution or retention failure materially breaks a supported security workflow. | Caller-chosen capture suppression and operator purge can be authorized behavior. |
| Low | Limited metadata leakage or local administrative inconvenience. | A correlation ID under user control is not an authenticated credential and is not itself a security defect. |

This model uses an independent source-backed architecture pass. Repository citations were checked against the supplied inventory and source lines; application code and external services were not executed. Source-established behavior is distinct from unverified deployment exposure. Revisit the model when the described input, storage, authorization or publication boundaries change.
